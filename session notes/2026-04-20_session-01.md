## 3. Important decisions made

- The canonical reporting engine assumptions were fixed deliberately so future comparisons use one stable methodology instead of mixed legacy variants. The key assumptions are hourly signals, hourly prices, prior-bar execution, 5 bps subtractive switch cost, daily-resampled metrics, and 365-day CAGR.
- Improved ALFRED was still adopted even though the canonical corrected-ALFRED comparison showed slightly worse Sharpe / Sortino and worse drawdown. The reason was that the change corrected a real upstream data defect, slightly improved final value / CAGR, reduced switching, lengthened holding periods, and improved monitoring/data-lineage fidelity.
- Production adoption used data logic update plus retrain/promotion together rather than data-only adoption. This avoided train/serve mismatch and ensured the promoted model, production silver state, and live monitoring all reflected the same corrected macro history.
- Production/live state and `main` were explicitly aligned because the repo branch used for release, the Databricks repo branch, and the executed workspace notebooks had diverged during the validation/release cycle. Leaving that divergence in place would have made future operational work error-prone.
- Dashboard cleanup was treated as presentation work rather than release logic. That separation kept the production bug fix and retrain release focused, while allowing the dashboard to be cleaned up later without reopening model/data release decisions.
