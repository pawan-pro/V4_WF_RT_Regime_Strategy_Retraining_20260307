## MUB-16 — Token refresher timeout hardening

### Objective

Harden the standalone Saxo token refresher so timeouts during refresh are treated as ambiguous token-chain state rather than silently continuing into repeated invalid-refresh failures.

### Workflow

- Symphony posted useful scope confirmation and a material finding: the live refresher and OAuth bootstrap still have hardcoded client credentials, but secret migration was deliberately kept out of MUB-16 to preserve narrow scope.
- Codex then continued MUB-16 manually with a one-file patch.

### Patch outcome

- PR #3: `[MUB-16] Harden Saxo token refresh timeout handling`
- Branch: `codex/MUB-16-codex`
- Commit: `db18d4f17d0cffb2a4e58f3cf7bd8829864b0e41`
- Changed file: `01_Processing/05_Utilities/09_RT_Saxo_Token_Refresher_Standalone_Job.py`
- PR #3 was marked ready and merged into `feat/live-macro-phase1-pce-gdp-overrides`.
- Merge commit shown in GitHub: `6c55266...`

### Behavior added

- Catch request timeout classes around the Saxo token refresh POST.
- Treat timeout as ambiguous token-chain state.
- Do not overwrite canonical token state on timeout.
- Write only non-secret incident metadata.
- Fail with a clear actionable error.
- Preserve:
  - valid-token skip path
  - atomic success write
  - existing 401 OAuth-chain-broken behavior
  - lock cleanup in `finally`
  - single-writer invariant

Validation was intentionally limited to static syntax check because OAuth/bootstrap could not be safely rerun again that night:

- `python3 -m py_compile 01_Processing/05_Utilities/09_RT_Saxo_Token_Refresher_Standalone_Job.py`
- No real token refresh forced.
- No OAuth bootstrap run.
- No token values inspected, printed, rotated, or exposed.

### Objective

Clarify the stakeholder report so it distinguishes:

1. Model target allocation
2. Actual Saxo holding
3. Position market value
4. Estimated uninvested/unallocated equity
5. Execution status

### Background

During MUB-13 review, the report showed `100% QQQ` as the position and cash/balance fields around `$4,807`, while the account actually held 5 QQQ shares and later top-up attempts were skipped due to Saxo minimum-order/cash precheck constraints.

- Actual holding: 5 QQQ shares.

- Saxo-reported `account_cash` / `account_balance` fields should not be displayed as residual uninvested cash in the main KPI grid.

Throughout the session, we continued to distinguish:

1. Git branch / PR state
2. Databricks Repo metadata
